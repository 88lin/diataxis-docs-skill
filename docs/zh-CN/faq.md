# 关于适用范围与设计的问题

这个 Skill 为什么存在、刻意不做什么，以及它和让助手"把文档写好"有什么区别。

## 为什么需要这个 Skill？

大多数文档问题是分类问题，不是写作问题。

当一个页面同时要教新手入门、指导熟练用户完成任务、罗列 API 字段、解释设计取舍时，每一类读者都会受损：新手找不到那节课，熟练用户找不到步骤，专家找不到他要查的那个字段，维护者不知道新内容该放哪里。文字可以写得很漂亮，页面照样是失败的。

Diataxis 的做法是在动笔之前先问两个问题：这段内容是指导行动还是传递认知？它服务于习得技能还是应用技能？答案会指向四种类型中的唯一一种。这个 Skill 把这两个问题变成助手在起草之前就会执行的动作。

## 它是不是就是 Diataxis 官网的摘要？

不是。Diataxis 是给人用的框架，这个 Skill 是给模型用的作业规程。

它额外提供了：触发条件的定义，让助手知道框架何时适用；分文体的反模式清单，让它知道要避开什么；蓝图，让每种类型都有起始结构；到 Good Docs Project 模板的映射，让相邻文档类型也有归属；以及处理大型体系的方案，避免它试图一次重写整个文档站。

## 它和通用写作助手有什么区别？

通用助手优化的是流畅的文字，这个 Skill 优化的是**正确的文档类型**。

| 通用写作助手 | 这个 Skill |
| --- | --- |
| "这是一个写得不错的文档页面。" | "这是适合这位读者的那一类页面。" |
| 把请求当作写作任务。 | 把请求当作分类任务。 |
| 默认把多种形态混在一起。 | 拆分并删减，保证一页一种形态。 |
| 鼓励覆盖得越全越好。 | 鼓励聚焦的页面加上互相链接。 |
| 不告诉你要避开什么。 | 提供明确的反模式清单。 |
| 以文字质量衡量。 | 以分类准确度和形态分离度衡量。 |

如果你只想要流畅的文字，不需要这个 Skill。如果你想要文档的**形状**是对的，那就需要。

## 什么时候不该用它？

这个 Skill 的范围是刻意收窄的。以下场景请不要用它：市场文案和博客；线框图、幻灯片这类视觉产物；代码审查和实现工作；不需要文档结构的简短回答；以及翻译已经结构良好的文档。

一个有用的判据：如果请求更关心*说什么*而不是*该写成哪一类文档*，那就超出范围了。仓库里附带了明确的 non-trigger 评测项，所以这条边界是被测试过的，而不是靠假设。

## 它会取代作者吗？

不会。它改善的是助手关于"该写哪类文档"的首稿判断。准确性、语气、产品知识和最终结构仍然归你。Skill 无法判断一句关于你产品的陈述是否属实。

## 需要先懂 Diataxis 才能用吗？

不需要。决策树、反模式清单和蓝图都是按"没读过原始资料也能用"来写的。读一读 [diataxis.fr](https://diataxis.fr/) 会让你更善于判断输出质量，但那不是拿到有用输出的前提。

## 支持哪些语言？

框架本身与语言无关，Skill 会用你书写的语言来应用它。仓库自带的文档是中英双语的。`references/zh-cn-anti-patterns.md` 覆盖了中文技术写作特有的失败模式——有些反模式并不能跨语言迁移。

## 它会帮我写代码示例吗？

只在教程或参考文档里，并且只在该文体确实需要示例时。选定文体是 Skill 的职责，代码的正确性是你的职责，因为只有你能运行它。

## Skill 是怎么评测的？

[`evals/evals.json`](../../evals/evals.json) 收录了 13 个分类下的 35 条提示词：classification、single-page-classification、mixed-form-detection、per-form-writing、decision-framework、review、migration、large-system、adjacent-types、anti-pattern-avoidance、tool-use、localization、non-trigger。

每条评测把一个真实的提示词和一份"正确答案应有的形状"配成一对。评分是人工的——由人或模型阅读回答并判断。没有自动打分器，所以请把这些评测当作回归检查清单，而不是一个基准分数。新增评测的方法见 [开发与贡献](development.md#新增评测项)。

## Skill 文件为什么这么长？

因为它是模型随时查阅的参考资料，不是给人从头读到尾的页面。但每一行仍然是每次使用都要付的成本，所以 CI 把这个文件限制在 500 行以内，细节放进 `references/`——Skill 只在需要时才链接并加载它们。

同样的道理也决定了导出到其他助手时的做法，见 [上下文成本](ide-integration.md#上下文成本)。

## 可以通过 `skills.paths` 从任意 checkout 安装吗？

不可以。OpenCode 没有定义 `skills.paths` 配置项。请把 checkout 放进文档列出的项目级或全局 Skill 目录；也可以把其他位置的 checkout 复制或链接到这些目录。存放它的目录仍须命名为 `diataxis-docs`，与 frontmatter 里的 `name` 一致。支持的安装位置见[安装 Skill](installation.md#安装到-opencode)。

## 为什么导出到 Claude Code 时不写 CLAUDE.md？

因为 `CLAUDE.md` 是常驻上下文：它会被拼接到该项目的每一次请求前面，包括与文档毫不相关的请求。整份指南约 3,500 tokens，按每次请求计费。

Claude Code 原生支持 Skill，宿主只在请求与 Skill 描述匹配时才加载它，所以默认的 `claude` 导出目标写的是 `.claude/skills/diataxis-docs/SKILL.md`。常驻写法仍然保留为需要显式选择的 `claude-md` 目标，供读取 `CLAUDE.md` 但不支持 Skill 的宿主使用。详见 [上下文成本](ide-integration.md#上下文成本)。
